三之一、關鍵議題詳細說明

1. 主約層級理賠代碼映射

問題本質

保險契約通常包含一張主約與多張附約。實際理賠可能由特定附約觸發，但理賠狀態、拒賠代碼或調查結果可能僅記錄於主約層級。若直接把主約結果套用至所有附約，容易造成錯誤貼標、重複計算或無法辨識真正異常的保障責任。

典型風險情境

  • 實際僅醫療附約拒賠，但主約與其他附約均被標記為拒賠。
  • 同一理賠案件同時存在給付、部分給付及拒賠，卻被簡化為單一結果。
  • 拒賠原因只存在於人工備註，結構化欄位無法對應到具體附約或給付項目。
  • 舊系統與新系統的代碼定義不同，造成歷史資料口徑不一致。

必要映射關係

保單號碼 → 主約號碼 → 附約號碼 → 理賠案件號碼 → 理賠申請項目 → 給付責任 → 理賠決定 → 拒賠原因。

建議建立的標準欄位

Policy_ID、Main_Contract_ID、Rider_ID、Claim_ID、Claim_Item_ID、Coverage_Code、Claim_Result_Code、Denial_Reason_Code、Investigation_Flag、Substantive_Denial_Flag。

應追蹤

  1. 理賠結果實際記錄於案件層、保單層、主約層或給付項目層。
  2. 一個 Claim_ID 是否可對應多張附約。
  3. 同一案件是否可能同時存在給付、部分給付與拒賠。
  4. 拒賠原因是否能對應到具體附約與保障責任。
  5. 歷史系統與現行系統的代碼是否一致。
  6. 無法映射案件的比例、原因與處理規則。

建議驗收標準

  • 每筆模型資料可追溯至具體理賠案件與保障責任。
  • 不以主約結果錯誤覆蓋所有附約。
  • 部分給付案件具備明確貼標規則。
  • 無法映射案件須量化並建立例外處理。
  • 可設定參考 KPI：主附約映射成功率 ≥99%、理賠項目映射成功率 ≥98%、拒賠原因可辨識率 ≥95%。實際門檻仍應依各公司資料現況核定。

2. 理賠資料完整性

問題本質

模型不只需要最終理賠結果，也需要完整的保單、被保人、理賠申請、醫療明細、調查過程、核賠決定、拒賠原因及歷史行為資料。資料存在不代表可用，還必須檢查欄位、案件、歷史期間、邏輯及跨表關聯是否完整。

五個完整性面向

  1. 欄位完整性：必要欄位是否存在，且非空率是否達標。
  2. 案件完整性：申請、醫療明細、調查、核賠與結案資料能否完整串接。
  3. 歷史期間完整性：近五年各年度的欄位品質是否一致，是否有系統轉換斷層。
  4. 邏輯完整性：日期、金額、住院天數、拒賠結果等是否符合業務邏輯。
  5. 跨表關聯完整性：Claim_ID、Policy_ID、Rider_ID、Hospital_Code、Diagnosis_Code 是否有孤兒資料。

建議建立 Data Quality Report

至少涵蓋 Completeness、Uniqueness、Validity、Consistency、Timeliness、Integrity 六類指標，並以年度、來源系統、商品、案件狀態及欄位分層檢視。

專案管理重點

需明確區分：可直接使用欄位、需清洗欄位、僅能當輔助欄位，以及不適合進入模型的欄位；並建立缺值處理、異常值處理、資料排除與補值規則。

3. ETL 流程是否可支援模型欄位

問題本質

現有 ETL 多以營運報表為目的，通常只產出案件數、理賠金額、拒賠件數及處理天數等彙總資訊；模型則需要更細的時間窗口、歷史行為與關聯特徵，因此必須確認既有 ETL 是否能支援多來源整合、歷史聚合、時間點正確性、增量更新及可重跑。

模型可能需要的衍生欄位

  • 過去 30／90／180／365 日理賠次數與累計金額。
  • 相同醫院、醫師或診療項目的歷史拒賠率。
  • 保單生效日至首次理賠天數。
  • 被保人跨院所、跨商品或短期重複申請次數。
  • 同一事件對應多張附約或多項給付的聚合特徵。

ETL 必備能力

  1. 多來源整合：保單、理賠、醫療明細、調查、客戶、商品及院所主檔。
  2. 防止 Data Leakage：只能使用預測時間點以前已知的資訊。
  3. 歷史窗口計算：支援不同觀察期間與截至日。
  4. 可重跑與一致性：同一輸入、同一版本產生相同結果。
  5. 增量更新：支援 Full Load、Incremental Load、Backfill 與 Reprocessing。

應要求的文件

Source-to-Target Mapping、ETL 規格書、Feature Definition Document、Data Lineage、批次依賴圖、錯誤處理與重跑機制、欄位驗證規則及上下游影響分析。

4. 是否可追溯完整理賠生命週期

問題本質

理賠案件並非只有申請與結案兩個狀態，而是由事故發生、申請、收件、補件、初審、發查、調查、核賠、給付或拒賠、申訴、覆核及最終結案等事件構成。若僅保存最終狀態，將無法還原決策過程、判斷特徵生成時間或說明模型預測。

建議生命週期事件

事故發生 → 理賠申請 → 文件收件 → 文件補件 → 初步審核 → 發查 → 調查進行 → 調查結果 → 核賠決策 → 給付／部分給付／拒賠 → 申訴 → 覆核 → 最終結案。

建議建立 Claim Event Table

主要欄位包括 Claim_ID、Event_Type、Event_Time、Event_Result、Operator_Unit、Source_System、Event_Version。以事件表保存每次狀態變更，可支援案件時序分析、流程瓶頸分析與稽核追溯。

需先明確定義的複雜情況

  • 一案多次決策：初次拒賠後申訴改判，Y 應採初次、最終或申訴後結果。
  • 一案多項給付：同一案件部分給付、部分拒賠，需決定模型粒度。
  • 案件重開或補件：需區分新事件、舊事件及狀態覆蓋。
  • 多系統時間戳：需統一時區、格式與事件先後順序。

追溯能力驗收

任一模型預測結果應能追溯至 Feature 數值、計算邏輯、ETL 批次、來源欄位、原始理賠案件及預測當時的案件狀態。此能力是模型治理、稽核、申訴處理與模型說明的重要基礎。

5. 建立可重複更新的 Feature Pipeline

問題本質

Feature Pipeline 不是一次性產出訓練資料，而是建立可持續執行、可版本化、可監控、可重跑的特徵生產流程。聯邦式學習更要求各公司在欄位名稱、資料型態、單位、時間窗口、缺值處理及類別編碼上維持一致。

建議資料層次

Raw Layer（原始資料） → Standardized Layer（格式與代碼標準化） → Curated Layer（清洗與關聯） → Feature Layer（衍生及聚合特徵） → Training Dataset（訓練資料） → Batch／Online Scoring Dataset（評分資料）。

每個 Feature 應具備的定義

Feature Name、中文名稱、商業定義、計算公式、資料粒度、觀察窗口、排除條件、Null 處理、更新頻率、來源欄位、負責單位、版本及生效日期。

企業級能力要求

  1. 版本管理：Feature 變更不得直接覆蓋舊版，模型須記錄所使用版本。
  2. 自動化測試：檢查欄位缺失、型態變更、Null率、資料量、重複鍵與分布漂移。
  3. 訓練與評分一致：避免 Training-Serving Skew。
  4. 節點一致性：各參與公司需使用一致欄位口徑與轉換規則。
  5. 監控及重跑：具備排程、日誌、失敗告警、補數與重算機制。

管理清單

Feature Catalog、Feature Definition、Version Control、Data Quality、Data Lineage、Refresh SLA、Failure Handling、Access Control、Node Consistency。

五項議題的管理優先順序

建議執行順序

  1. 確認模型粒度與 Y 定義。
  2. 完成主約、附約、案件及給付項目映射。
  3. 盤點資料完整性與歷史可用期間。
  4. 建立理賠生命週期及 Data Lineage。
  5. 設計 Feature 與 ETL 規格。
  6. 建立可重跑、可監控、可版本化的 Feature Pipeline。

核心決策

核心決策

模型的一筆資料究竟代表一個理賠案件、一張附約，還是一個給付項目，必須在資料盤點與 Feature 設計前先確定。若粒度未先定義，後續 Y 貼標、主附約映射、ETL、Feature 及模型評估都可能反覆重做。
